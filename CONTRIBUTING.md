# Contributing

Keep the local training loop simple and testable.
Discuss changes to feedback meanings or mastery rules before changing them.

## Source and documentation

- Use short English sentences in comments and documents.
- Start each source file with a comment or module docstring about its purpose.
- Document every function and method. State inputs, outputs, logic, and dependencies.
- Put a purpose comment at the top of each text document and configuration file.
- Keep required format markers first. For example, Skill YAML frontmatter comes
  before the body. Put the purpose comment inside that frontmatter.
- Do not add comment-free formats when a suitable documented format exists.
- Do not commit generated bytecode, databases, logs, secrets, or private exports.

The runtime core uses the Python standard library.
Keep framework and client-specific code outside its rules and application service.
The planned frontend uses React with TypeScript. Its API adapter will use FastAPI.

## Validation

Run from the repository root:

```sh
python3.12 -m unittest discover -s tests -v
```

Add tests for observable behavior. Important cases include a lost response after
commit, duplicate operations, stale revisions, changed feedback, and plan reruns.
Do not add tests that merely repeat implementation details.
Use temporary directories and synthetic records.

When changing the Skill, also build it into a fresh temporary destination.
Run it from outside the checkout. A bundle must contain its own core.

## Data and rule changes

Explain how a rule change affects existing records.
Keep raw feedback history. Make schema and state-version changes explicit.
Verify that state can be rebuilt and that backup recovery still works.
Never treat model agreement as proof of correctness.

Catalog contributions may include IDs, tags, metadata, and official links.
Do not include full problem statements or paid content.
Do not contribute real practice records, chat logs, task IDs, personal paths,
authentication cookies, or deployment credentials.

## Pull requests

Describe the user-visible result and the checks you ran.
State any new runtime requirement or compatibility limit.
Keep unrelated changes separate. Do not publish user data as a demonstration.
